# Workout Analysis

## Атомарный запуск анализа без outbox и обработки старой истории
При первом переходе WorkoutSession в Completed создавать анализ Pending синхронно в той же внешней транзакции и на том же соединении БД; ошибку инициализации не подавлять. После commit отправлять Job, а ошибку доставки оставлять для recovery. Без transactional outbox и границы по дате: recovery работает только с существующими Pending/Processing и никогда не создаёт анализ для отсутствующего. Повтор Failed доступен только служебной команде. В Redis округлять availableAt вверх до целой секунды, сохраняя микросекунды доменного scheduledAt.

## Первый запуск анализа без задержки
Первую попытку отправлять сразу после commit без delay. Задержки 5 и 30 секунд сохраняются для автоматических повторов; применять delay и округление времени вверх только если attemptNumber > 1 и availableAt ещё в будущем. Уже наступившие повторы отправлять немедленно.

## Публичное чтение анализа не запускает обработку
GET анализа по ID сессии только читает сохранённый результат владельца; чужой и отсутствующий анализ дают одинаковый 404. Не создавать отсутствующий анализ при чтении и не добавлять публичный retry. Сейчас status отражает только этап сравнения: completed не означает наличие ИИ-заключения или рекомендаций. Историю попыток не раскрывать; веса и объём на HTTP-границе в кг, даты UTC.

## Recovery запускается вручную
По решению пользователя не регистрировать workout-analysis:recover в Laravel Scheduler. Команда остаётся доступна для ручного запуска; schedule:work для анализа не требуется. После потери Job или зависания Processing восстановление требует запуска этой команды.

## Неизменяемый контекст и согласованное чтение истории
Подготовку контекста выполнять внутри AnalysisTransaction на том же соединении, под общей блокировкой строки пользователя; будущие записи ИИ-результатов и рекомендаций должны соблюдать этот протокол. История: два независимых окна той же/остальных программ, строго completedAt < текущего, последние по completedAt DESC, id DESC перед лимитом. После сохранения context не пересобирать при повторах или изменении истории/настроек. Фиксировать применение рекомендации к плану; не вводить признак её фактического использования или связь с упражнением последующей сессии.

## Отдельный этап заключения ИИ и безопасные повторы
Создавать Pending этап ИИ атомарно с завершением сравнения; отправлять Job после commit. Сетевой запрос выполняется вне транзакции по зафиксированному контексту; сохранять ответ только текущей действующей попытки. API status/result остаются сравнением, ai_analysis публикуется отдельно. Автоповторы только временных ошибок; отказ/неполный/недопустимый ответ — явная ошибка со служебным retry-ai. Не логировать ключи или тела ответа провайдера; старые готовые анализы не дополнять ИИ автоматически.

## Полная цепочка рекомендаций и неизменяемые исходные данные
До первого запроса ИИ атомарно фиксировать историю, программу, каталог и счётчики допуска; второй запрос и все повторы используют сохранённый контекст. Третий этап имеет отдельные попытки/Job/recovery. status/result API сохраняют сравнение; overall_status охватывает три этапа, recommendation_generation публикуется отдельно. Предложения применяются по одному атомарно к плану; не вводить признак фактического использования в тренировке.
