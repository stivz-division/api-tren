# API тренировок

Laravel API для Telegram Mini App, в котором клиент составляет недельное расписание тренировок, фиксирует выполнение выбранной программы и получает сравнение плана с фактом.

План программы хранится отдельно от тренировочной сессии: изменения расписания не переписывают уже начатую или завершённую тренировку.

## Анализ тренировок

После первого завершения всей тренировочной сессии автоматически создаётся анализ. В фоне рассчитываются отклонения по подходам, повторениям и объёму нагрузки на уровне тренировки, упражнений и порядковых пар подходов. После сравнения отдельная Job запрашивает заключение OpenAI по этой тренировке и доступной истории. Рекомендации по изменению программы пока не реализованы.

Авторизованный клиент получает статус и результат своей тренировки через:

```http
GET /api/workout-sessions/51/analysis
```

Нужен Bearer-токен, полученный через Telegram-аутентификацию. Ответ содержит `data.id`, `workout_session_id`, `status`, `failure_code` и `result`. Состояния: `pending`, `processing`, `completed`, `failed`; результат доступен при `completed`, иначе `null`. Код ошибки доступен только при `failed`. Эти поля по-прежнему описывают сравнение плана и факта. Отдельное поле `ai_analysis` содержит статус, код ошибки и результат этапа ИИ (`current_workout`, `history`, `evidence`); до создания этапа и у старых анализов оно равно `null`. Ошибка ИИ не скрывает числовое сравнение.

Вес в `working_weight_kg` и объём в `volume_kg` передаются в килограммах; объём — сумма веса × повторения. Каждое отклонение содержит `planned`, `actual`, `difference` и `percentage`; процент равен `null`, если плановое значение нулевое. Даты анализа возвращаются в UTC. Полная структура ответа описана в [OpenAPI](openapi.json).

Чужой и отсутствующий анализ возвращают одинаковый `404 workout_analysis_not_found`. Чтение не создаёт анализ; старые завершённые тренировки автоматически не обрабатываются. Публичного запуска и повтора анализа нет.

## Фоновая обработка

После установки зависимостей и настройки `.env` примените миграции:

```bash
php artisan migrate
```

Для конфигурации по умолчанию нужны PostgreSQL, Redis и постоянно работающий обработчик очереди:

```bash
php artisan queue:work redis --queue=workout-analysis --timeout=60
```

В Sail используйте `./vendor/bin/sail artisan` вместо `php artisan`. Соединение и имя очереди задаются в `config/workout-analysis.php` через `WORKOUT_ANALYSIS_QUEUE_CONNECTION` и `WORKOUT_ANALYSIS_QUEUE`; команда worker должна соответствовать этим настройкам.

Для заключений задайте `OPENAI_API_KEY` в окружении сервера. Модель задаётся через `WORKOUT_ANALYSIS_AI_MODEL` (по умолчанию `gpt-5.4-mini`). После обновления примените миграции и перезапустите worker. Ключ остаётся на сервере; тесты используют подставные HTTP-ответы.

Контекст сохраняется перед первым запросом: текущие отклонения и два независимых окна истории (по 20 тренировок по умолчанию). Повторы используют тот же снимок. OpenAI получает план, факт и доступные исторические выводы; идентификатор пользователя не передаётся. Для Responses API задано `store: false`. При превышении лимита входных данных контекст не обрезается молча: этап завершается ошибкой.

Первый запуск отправляется сразу после commit. Восстановление ожидающих и зависших анализов выполняется вручную командой `php artisan workout-analysis:recover`; задача по расписанию не зарегистрирована. Для повторных попыток сохраняются задержки 5 и 30 секунд. Для ИИ автоматически повторяются сетевые сбои, 429/5xx и истёкшие попытки (до 3 попыток); отказ, неполный или недопустимый ответ остаются явной ошибкой. Ошибка подготовки контекста требует служебного повтора после устранения причины. Повтор этапа ИИ: `php artisan workout-analysis:retry-ai 1`. Общая команда `workout-analysis:recover` восстанавливает оба этапа; готовые старые анализы не дополняются ИИ автоматически.

Ручной повтор неудачного сравнения доступен служебной команде `php artisan workout-analysis:retry 1`, где `1` — ID анализа, а не тренировки.
